# Перенос бизнес-данных Теплосферы

## Назначение и границы

Импорт PostgreSQL custom dump старой Теплосферы в самостоятельное приложение Go/Vue. PHP и работающий старый сервис не требуются. Скрипт создаёт отдельную временную БД, преобразует данные, сверяет их и публикует результат одной транзакцией **только в пустую целевую БД**. Перенос поверх существующих записей и повторный импорт запрещены.

Требования: Docker и PostgreSQL 16+. Цели `make migrate-plan`, `make migrate-dump` и `make test-migration` выполняются в образе `tsfera-tools` (`docker/tools/Dockerfile`: Go согласно `backend/go.mod`, Python 3, `bsdtar`, `psql`/`pg_restore`/`pg_dump` PostgreSQL 16 из репозитория PGDG — под версию сервера из `docker-compose.yml`: `pg_restore` 17 при сервере 16 падает на `SET transaction_timeout`); образ собирается автоматически. Контейнер работает в сети хоста (`MIGRATION_DOCKER_NETWORK=host`), поэтому `localhost` в URL указывает на БД хоста. На macOS для этого в Docker Desktop должен быть включён host networking, иначе указывайте `host.docker.internal`. Каталоги `DUMP`, `PERMISSION_MAP`, `MIGRATION_FILES_ROOT` и родитель `MIGRATION_FILES_DESTINATION` монтируются в контейнер по тем же путям. Временные файлы и приватный журнал пишутся в `.cache/tmp`. При запуске `scripts/migration/migrate.py` без Docker нужны Python 3.9+, Go и утилиты PostgreSQL, совместимые с версией дампа; `PG_BIN` задаёт каталог утилит. Учётная запись `MIGRATION_ADMIN_URL` должна создавать/удалять временные БД. Предусмотреть место для исходной копии, преобразованных данных, индексов, WAL и SQL-снимка. Приложение и фоновые задания запускать после переноса.

## Команды

Для системы из `docker-compose.yml` достаточно `make` (первичный импорт) и `make deploy-dump` (замена данных новым дампом); см. README. Ниже — ручной запуск против произвольного сервера PostgreSQL.

URL передаются через переменные окружения, не через параметры процессов. Значения ниже — примеры, не рабочие пароли.

```sh
export MIGRATION_ADMIN_URL='postgresql://migration:password@localhost:5432/postgres?sslmode=require'
export MIGRATION_DATABASE_URL='postgresql://migration:password@localhost:5432/tsfera_new?sslmode=require'
make migrate-plan DUMP=/path/to/backup.dump
```

`migrate-plan` не меняет целевую БД. Код 0 — проверки пройдены и препятствий нет; 2 — преобразование проверено, но отсутствуют файлы/сопоставления прав; 1 — ошибка. Отчёт `migration-report.json` содержит SHA-256 дампа, количества строк, назначения таблиц, неполные записи, исходные повреждённые ссылки и препятствия. Он закрыт правами 0600 и исключён из Git. Можно задать `MIGRATION_REPORT`.

Для файлов требуется копия исходного файлового хранилища: относительные пути должны совпадать с `ref_file.storage_key`. Каждая запись проверяется по размеру, содержимое — SHA-256. Если по ключу с расширением `.jpg`/`.jpeg` файла нет, берётся файл с другим написанием расширения и тем же размером; в назначение он копируется под ключом из БД, а в отчёте помечается `extension_normalized`. С `ALLOW_MISSING_FILES=1` неполное хранилище допустимо: найденные файлы переносятся, отсутствующие помечаются в отчёте `missing` и попадают в предупреждение с их числом. Скрипт запрещает выход за корень, абсолютные пути и перезапись существующего каталога назначения.

```sh
export MIGRATION_FILES_ROOT=/backups/teplosfera-files
export MIGRATION_FILES_DESTINATION=/srv/tsfera/imported-files
make migrate-dump DUMP=/path/to/backup.dump
```

После переноса приложение должно использовать этот каталог как `TSFERA_STORAGE_DIR` (в контейнере смонтировать его в `/data/attachments`). Если публикация БД не удалась, скопированные файлы сохраняются: скрипт не удаляет содержимое, которое могло стать доступным после неопределённого сетевого сбоя. Повторное копирование требует нового каталога; существующий не перезаписывается.

Встроенная карта `backend/pkg/platform/migration_permissions.json` автоматически сопоставляет все 112 разрешений данного дампа. Наследование раскрывается в итоговый набор прав каждой из 9 ролей; 103 назначения пользователям сверяются в SQL в обе стороны. Роли сохраняются как `legacy_<исходный ID>` с исходным названием в описании. В отчёт добавлен раздел `permissions`.

`PERMISSION_MAP=/secure/permission-map.json` нужен только для переопределения встроенной карты либо новых разрешений другого дампа. Это JSON вида `{"common.application_for_technical_work.view":["crm.application.view"]}`. Пустой список явно отключает соответствующее старое разрешение. Неизвестные новые разрешения отклоняются. Иерархия ролей и назначения пользователям переносятся; старое имя `superadmin` не даёт автоматического неограниченного доступа. Для первого администрирования задайте `TSFERA_ADMIN_USER` с **новым, отсутствующим** именем и сильный `TSFERA_ADMIN_PASSWORD`, затем настройте доступ. Старые хеши паролей пользователей сохраняются, сессии — нет.

Только для осознанного переноса метаданных без файлов:

```sh
make migrate-plan DUMP=/path/to/backup.dump ALLOW_MISSING_FILES=1
make migrate-dump DUMP=/path/to/backup.dump ALLOW_MISSING_FILES=1
```

`ALLOW_MISSING_FILES=1` **не восстанавливает** отсутствующие файлы; при заданном `MIGRATION_FILES_ROOT` переносит те, что есть. Неизвестные разрешения другого дампа блокируют импорт; `ALLOW_UNMAPPED_PERMISSIONS=1` явно разрешает их пропуск и для проверенного дампа не нужен. SIP-секреты и аудиозаписи, не входящие в дамп, из него восстановить нельзя.

## Правила сохранения данных

- Прямые сущности сохраняют ID, даты, номера, суммы, состояние удаления, авторов и связи. Проверяется каждое преобразуемое поле каждой записи, а не только количество строк.
- `crm_application_phones` хранит связи заявок с телефонами; `crm_certificate_equipments` — оборудование актов и серийные номера. Эти связи возвращаются API и доступны в данных документов; календарь учитывает телефоны конкретной заявки.
- `crm_change_logs` содержит историю изменений с преобразованными типами сущностей и исходными ID. История не считается техническим мусором.
- Дополнительные исходные бизнес-реквизиты сохраняются в `source_data`, полные строки вложенных таблиц — в `source_relations`. Это неизменяемые сведения **на момент импорта**, а не актуальные значения после последующего редактирования. Они позволяют сохранить исходные NULL, авторов, ID строк и детали, отсутствующие в упрощённых моделях. Для заявок и актов предусмотрен просмотр в интерфейсе.
- Справочники объединяются по виду; их исходные ID остаются в `source_data`. `crm_import_enums` сохраняет значения и смысл исходных перечислений.
- Категория клиента `client_category_id` хранится отдельно от признака физического/юридического лица. Классификации звонков используют пространство кодов `1000 + исходный ID` и `import_<ID>`, чтобы одинаковые числа не меняли смысл.
- Двойное JSON-кодирование результатов актов и настроек раскрывается. Ответы «Да»/«Нет» преобразуются в boolean; пустое значение остаётся неизвестным. Исходное представление сохранено. Свободный текст о запчастях не превращается в выдуманные позиции и количества.
- Повторные записи пула пропущенных звонков объединяются по `(call_id,user_id)`; все исходные строки сохраняются в `source_relations.original_rows`. Непросмотренное состояние сохраняется, если хотя бы одна исходная запись не просмотрена.
- Пустые адреса, контрагенты и сроки не заполняются вымышленными данными. Для отсутствующей записи телефона сохраняется `unresolved_phone_id`, рабочий внешний ключ остаётся NULL; такая ситуация отражается в отчёте.

Не переносятся `migration`, `sys_token`, `sys_auth_rule`, `reg_task_pool`, `reg_queue_user`, `reg_user_setting`: история PHP-миграций, токены, исполняемое правило старой авторизации, внутреннее состояние очередей и настройки старого интерфейса. Поле `ref_user.auth_key` исключается. Неизвестная исходная таблица останавливает импорт, вместо молчаливого пропуска. Временная схема `legacy_import` удаляется перед публикацией: приложение не зависит от старых таблиц.

## Проверка

```sh
make test-migration
make test-backend
make test-frontend
# Только для отдельной БД, уже полученной импортом реального дампа:
cd backend
MIGRATION_TEST_DATABASE_URL='postgresql://...' go test ./internal/modules/crm -run TestImportedDatabase -count=1 -v
```

Интеграционный тест читает списки основных сущностей, неполную заявку и календарь, задачу без срока, акт с оборудованием и типизированными замерами, историю контрагентов. Проверки запускаются без сервера и фоновых заданий. Реальный дамп, файлы клиентов, SQL-снимки и приватные отчёты не добавляются в репозиторий.

## Результат проверки дампа 2026-11-14

Полный прогон выполнен на изолированном PostgreSQL 16.16: из 75 таблиц 69 преобразованы, 6 таблиц состояния исключены. Успешно опубликован снимок в пустую тестовую БД и выполнены проверки чтения через Go-репозитории. Рабочая БД не изменялась.

| Данные | Записей после переноса |
|---|---:|
| Заявки | 120 934 |
| Акты | 99 298 |
| Задачи | 75 504 |
| Звонки | 678 755 |
| Связи заявок с телефонами | 125 378 |
| Оборудование актов | 117 384 |
| История изменений | 1 184 222 |
| Метаданные файлов | 1 279 |

425 заявок имеют незаполненный адрес и/или контрагента; 55 495 задач — пустой срок. Одна исходная ссылка ведёт на отсутствующую запись телефона: исходный ID сохранён и отмечен как неразрешённый. В пуле пропущенных звонков 49 943 исходные строки сгруппированы в 49 395 рабочих записей; все исходные строки проверены и сохранены.

Отдельно проверены: отказ при повторном импорте через `make`, неизменность заполненной БД, откат ошибочной транзакции, обнаружение повреждения поля и связи при неизменном числе строк. Первоначальная тестовая публикация выполнялась с исключениями для файлов и прав. После добавления автоматической карты отдельно проверены перенос всех ролей и назначений на реальной БД, соответствие наборов прав и HTTP-ограничения. Повторный полный `migrate-plan` с реальным дампом завершился с кодом 0, `verified=true`, без несопоставленных разрешений и без `ALLOW_UNMAPPED_PERMISSIONS`; использован только `ALLOW_MISSING_FILES=1`. Наличие файлов этим не подтверждается.

## Разграничение действий после переноса

- Просмотр пула отделён от изменения правил и ручного запуска планировщика.
- Выполнение задачи, закрытие заявки, оценка, изменение комментария и экспорт проверяются отдельными разрешениями. Узкий PATCH комментария не изменяет другие реквизиты заявки.
- У каждого отчёта собственное разрешение; выбор чужого подразделения требует разрешения именно этого отчёта. Календарь отдельно проверяет выбор сотрудника и подразделения.
- Права на создание, изменение и удаление справочников проверяются по конкретному виду, включая оснащение сотрудников.
- Старый `superadmin` получает конечный набор исходных прав, а не глобальный `*`. Новые модули документации, чата, ИИ и управление доступом к моделям требуют отдельной настройки администратором новой платформы.
- Карта переносит разрешения, но не создаёт отсутствующие бизнес-операции. Например, регистрация исходных прав удаления SIP-аккаунта и редактирования оснащения не означает появления соответствующих API: эти операции требуют отдельной реализации. Полный функциональный паритет со старым приложением этим изменением не заявляется.

Проверочные роли и их иерархия в `scripts/migration/fixtures` содержат только названия ролей, разрешения и связи между ними; пользовательских записей и паролей в Git нет.
